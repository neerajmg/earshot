# QA audit, 2026-08-28

**Historical.** Every defect below was fixed in `04ac77c` and the commits after
it; a second, adversarial pass then found two more that those fixes had
introduced. This is the record of what was wrong on 2026-08-28, not a list of
open problems. Each defect now has a named regression test.

Three independent reviews of commit `1da4e88` — code quality, usability, and an
end-to-end functional run — before tagging v1.0.0. Recorded here because the
findings shaped the fixes that follow, and because the repro scripts lived only
in a temporary directory.

Method: the functional run drove Node-level transfers through `air.js`, the
worker message protocol through `createWorkerCore`, and the real page in
headless Chrome with a WAV as a fake microphone. No real speakers or
microphones were involved; that gap is noted at the end.

## What held up

The signal path did well under pressure, and this is worth stating precisely
because it is the part that was hardest to build:

- Every boundary size from 0 bytes to the 2 MB cap arrived byte-identical.
  The cap took 2731 frames against an estimate of 2733.
- 70 % frame loss, ±400 ppm clock offset, clipping to 0.1, gain 0.02× and 5×,
  a bad room with comb fading at 5 dB SNR, and the page's own 44.1 kHz chunked
  resampling path all delivered the file.
- The worker protocol survived every out-of-order message tried: `file` before
  `complete`, `file` twice, `push` before `init`, wrong passphrase then right.
- Both live selftests passed on the published URL with no JavaScript errors.
- Throughput 25 seconds of audio per CPU second; frame rendering 5 ms against
  a 2070 ms budget.
- Conventions verified consistent end to end: bit order, QPSK mapping, LLR sign
  and scaling, signalling lanes. All three ring buffers guard their readback.

## What did not

Two receiver states are reachable by a noisy channel and clear only on a page
reload, and one estimate is wrong by a factor of two:

| id | defect | evidence |
|---|---|---|
| H1 | A file CRC-32 mismatch latches a result that is never re-evaluated. The page says `received.`, stops the microphone, then says `transfer not complete`. | 12 subsequent correct frames change nothing; a fresh receiver recovers in 3 |
| H1b | One droplet with a corrupt payload and a colliding CRC-16 poisons a window permanently — it reaches full rank holding wrong bytes | a single 30 kB transfer through room echo plus comb fading produced 276 bad droplets, so the 2⁻¹⁶ collision is not hypothetical |
| H2 | A manifest that passes CRC-16 but is internally inconsistent throws `RangeError` from `fountain.js`, and is stored before the throw, so every later `push()` throws too. Uncaught in the worker; no `onerror` on the page | `winCount 5, size 300` |
| H3 | Files just over a 64 kB multiple cost about twice the airtime the page promises, because every window is fed equally regardless of how many blocks it holds | 65536 B → 86 frames; 65537 B → 171 against an estimate of 88; 100 kB → 171 against 136 |
| M5 | The 8-bit session field is sent and never checked, so two senders in one room make the receiver switch manifests every frame | 60 frames, 59 switches, 0 completions |
| M4 | The sender trims the passphrase and the receiver does not, so a trailing space — which phone keyboards add — locks the file | `pw` encrypts, `pw ` cannot open |
| M1 | The page never posts the `reset` the worker already supports, so re-sending the same file after a completed receive sits at 100 % forever | 10 frame messages, 0 completions |

Lower down: names over 64 UTF-8 bytes are cut silently, losing the extension and
sometimes splitting a codepoint; a whitespace-only passphrase ships the file in
the clear with no warning; the file name and size travel unencrypted even with a
passphrase, which the README does not admit.

## Usability

Two findings block a first-time phone user outright. Nothing on the page states
that both devices open the same page and one of them listens first — and the
Receive card starts about 870 CSS pixels down, below the fold on every phone
viewport tested, so the person who was sent the link sees a full screen of Send
with a disabled button. Separately, the file input is `display:none`, so it
never receives focus and cannot be reached by keyboard or switch access at all.

Below that: the send status contradicts itself past the estimate (`about 0 s
left` under a full bar, next to `keep going until the receiver has it`); the
progress bar sits 250 px below the button that starts it on a phone; the
receiver cannot distinguish listening from nothing arriving; the privacy warning
is truncated in a placeholder and buried below the fold; microphone failures
show raw browser strings; the received size is the compressed size; and the
pre-send estimate is three times pessimistic for text because compression is
only applied after the user commits.

A recurring theme: `docs/GUIDE.md` explains several things the page should say
itself — start the receiver first, what the transfer sounds like, that the
sender never stops on its own, that the size shown is post-compression.

## Not covered

Real speakers and microphones, real devices, and the Web Share branch of saving
a received file, all of which need hardware and a human. The over-the-air path
was last verified on the FSK engine; the OFDM engine has never been run through
actual air.
